\section{Introduction}

% Ensuring the correctness and safety of software systems often requires expressing and enforcing invariants—logical conditions that must hold over program state. These invariants can capture a wide range of requirements, including functional correctness, resource bounds, security policies, and consistency conditions. In many programs, such invariants are checked through runtime assertions, typically placed at the end of computations or after key operations. For example, a function may validate the result of a transformation or verify a condition just before returning. While such checks can detect violations, they may do so only after resources have been consumed or side effects have occurred, limiting the ability to prevent damage or recover cleanly.

% This pattern is particularly common in scripting and dynamic languages like Python, where lightweight development practices and permissive semantics often lead developers to write post-hoc assertions or ad-hoc validation logic. As a result, many programs only identify violations after executing significant logic—potentially propagating incorrect state, masking bugs, or allowing security-relevant errors to persist. A natural question arises: could such violations be detected earlier in the execution path, before unnecessary computation or effects take place?

Ensuring the correctness and safety of software systems often requires enforcing invariants through runtime assertions. These assertions typically appear at the end of computations, detecting violations only after resources have been consumed or side effects have occurred. This pattern is particularly common in dynamic languages like Python, where permissive semantics lead developers to write post-hoc validation logic, potentially allowing errors to propagate before detection. This raises a critical question: could violations be detected earlier in execution, before unnecessary computation occurs?

Existing approaches to this problem face significant limitations: static analysis tools struggle with Python's dynamic nature, manual refactoring is error-prone, and automated precondition inference often produces approximations that are either too strict or too lenient. The fundamental challenge lies in automatically transforming programs to detect violations earlier while preserving the exact logical guarantees of the original assertions.

We present SENTINEL, a novel approach that combines large language models for assertion generation with a multi-stage verification pipeline that guarantees logical equivalence between early and final checks. Our system enables more proactive error handling while maintaining program semantics. Experimental results demonstrate that early assertions can significantly reduce computational overhead—saving an average of 28.60 bytecode instructions per function—while preserving the original program's logical guarantees. We detail our motivations, results, and analysis further in the subsequent sections.

This paper investigates the technical feasibility and formal verification of \textit{early assertions}—assertions placed earlier in program execution that are logically equivalent to existing later checks (See Figure \ref{eq:assertion-equivalence}). Our research explores how to systematically transform programs to shift violation detection earlier while ensuring transformed assertions are neither overly strict nor overly weak.

We focus specifically on Python programs, where three factors make this problem particularly challenging: (1) dynamic typing that complicates static analysis, (2) implicit type conversions that can mask potential errors, and (3) complex control flow that creates multiple execution paths. Our approach leverages recent advances in LLMs to generate candidate assertions and combines symbolic execution, fuzzing, and formal verification to validate their correctness.

The central research question we address is: \textit{\textbf{How can we generate and formally verify early assertions in Python programs that are logically equivalent to existing later checks, ensuring critical security and correctness properties are maintained and potential violations are detected proactively?}} Through our systematic evaluation across functions of varying complexity, we demonstrate both the potential and limitations of automated early assertion transformation.

\subsection{Enforceable Security Policies and Early Assertion Placement}
Foundational work on security policy enforcement established that certain policies (notably safety properties) can be enforced at runtime by monitoring program executions and halting before a violation occurs \cite{schneider2000}. \textbf{Schneider's paper on enforceable security policies} formalized this notion, showing that execution monitors can insert runtime checks to stop an execution "when the security policy they enforce is about to be violated" \cite{schneider2000}. It is generally desirable to prevent execution as soon as a violation is detectable (although there are some situations in which desired computation occurs before the violation and after detection). Such inline reference monitors and runtime-checking frameworks (e.g., SASI, PoET/PSLang) demonstrated practical techniques for injecting security checks into code to enforce memory safety and access control policies at runtime. This fail-fast approach aligns with the principles of Design by Contract, where software components check preconditions at the interface and immediately flag contract violations rather than propagate errors \cite{meyer1992}. \textbf{Meyer's Design by Contract paradigm} introduced in the Eiffel programming language advocated that critical conditions be checked before or during execution of an operation, so that a violation is caught as early as possible, improving reliability \cite{meyer1992}.

These ideas underline our project's goal: by placing correct and equivalent assertions early in Python programs (at the point where a property can be evaluated), one can proactively detect potential correctness or security violations sooner, provided these early assertions enforce the same policy as existing late-stage checks.

\subsection{Static and Dynamic Verification for Python}
Fully static formal verification of Python programs is challenging due to dynamic typing and constructs. Nonetheless, recent research has produced tools that support user-specified assertions and specifications in Python. \textbf{Eilers' et al.'s Nagini paper} \cite{eilers2018} introduces a \textbf{sound static verifier for Python 3} that can prove memory safety, data race freedom, and user-supplied assertions in code. Nagini uses Mypy-style annotations and translates to the Viper intermediate verification language, supporting scalable modular reasoning. It was used to verify safety properties in production network code.

Complementary tools like \textbf{CrossHair} \cite{CrossHairTool} offer dynamic symbolic execution in native Python. CrossHair explores feasible paths and reports concrete counterexamples. It works well with minimal annotations, but is incomplete. We employ both: using CrossHair to detect mismatches between early and final assertions, and Nagini to formally verify equivalence under full specifications.

A related tool is \textbf{LLM-Sym} \cite{Wang2024-LLM-SymExec}, which uses LLMs to translate complex Python operations into SMT-compatible constraints, enabling symbolic execution to cover previously unsupported features such as dynamic list manipulation. While LLM-Sym improves symbolic reach, it still requires external verification to confirm semantic correctness-reaffirming our use of both dynamic and static techniques.

\subsection{LLMs for Assertion and Invariant Generation}

LLMs have become a common tool for assertion generation, but their approaches and guarantees vary widely. \textbf{Watson et al.} introduced ATLAS \cite{watson2020}, a neural machine translation model trained on unit test code, achieving 31\% exact matches with developer-written assertions. Recognizing its limitations—particularly with longer or uncommon assertions—\textbf{Yu et al.} \cite{yu2022} proposed a retrieval-augmented method that searches for semantically similar tests and adapts their assertions, yielding better accuracy and more interpretable outputs. While ATLAS attempts to learn general mappings, Yu's method grounds generation in past examples, making it more robust to out-of-distribution code.

Building on this idea, \textbf{Zhang et al.} \cite{zhang2024} developed RetriGen, combining a fine-tuned CodeT5 model with retrieval-based augmentation. By feeding the model both context and candidate assertions, RetriGen surpassed 57\% exact-match accuracy—significantly higher than prior models—and showed particular strength in longer, multi-condition asserts. Unlike Yu et al., Zhang incorporates retrieved examples into the model's input, letting it generalize more flexibly while still leveraging concrete cases.

Other directions include \textbf{Torkamani et al.} \cite{Torkamani2024-Assertify}, who use chain-of-thought prompting to synthesize inline production assertions directly from code, and \textbf{Li et al.} \cite{Li2025-LLM-Assertion-Gen}, who frame assertion generation as a code-repair problem. Both rely on retrieval-enhanced prompting to boost accuracy and generalization, but mainly target postconditions.

In contrast, \textbf{Pulavarthi et al.} \cite{Pulavarthi2024-LLM-HW-Assertions} test LLMs on synthesizing formal assertions for hardware verification. They find high variability: while models generate syntactically valid assertions, correctness often suffers, especially without sufficient in-context guidance—highlighting the brittleness of unconstrained generation.

\textbf{Pei et al.} \cite{Pei2023-LLM-Invariants} take a broader view, using LLMs to infer loop invariants from Java source code. Their model achieves high precision when trained on Daikon-mined datasets but struggles with pointer-heavy or structural invariants, showing the limits of purely pattern-driven learning.

While these works highlight the promise of LLMs in capturing developer intent, most focus on generating final-state or unit test assertions and evaluate success syntactically or via coverage metrics. Our work instead targets early assertion placement and enforces formal \(\phi_{early} \Leftrightarrow \phi_{final}\) equivalence. We don't just synthesize plausible assertions—we prove they preserve program behavior, bridging the gap between generation and correctness.


\subsection{Symbolic Execution, Fuzzing, and Hybrid Verification}
Symbolic execution tools like PyExZ3 and \textbf{CrossHair} \cite{ball2015, bruni2011} use SMT solvers to explore execution paths and check assertion satisfiability. Our system builds on CrossHair to verify that synthesized early assertions behave identically to final ones under all feasible paths. To complement it, we use \textbf{Hypothesis}, a property-based fuzzing library that generates randomized and edge-case inputs.

However, these methods are incomplete: symbolic execution may miss paths due to path explosion or unsupported features, while fuzzing offers no guarantees. We therefore incorporate \textbf{Nagini} \cite{eilers2018} to statically prove logical equivalence when specifications are expressible. This layered strategy mirrors neuro-symbolic frameworks like \textit{Driller}, combining broad bug exposure with formal rigor.

\textbf{Liu et al.} \cite{Liu2023-LLM-Sym-Inv} complement this strategy through LLM-SE, combining symbolic analysis and LLM-suggested invariants in a neuro-symbolic pipeline. Their system shows that integrating learned hypotheses into symbolic execution pipelines outperforms either method alone—validating our own hybrid verification approach.

\subsection{Precondition Inference and Logical Equivalence Guarantees}
Ensuring that early assertions are logically equivalent to final checks is a central goal of our work. \textbf{Schneider} \cite{schneider2000} defines enforceable safety properties as those that must hold for all prefixes of execution. This principle motivates early assertion placement when violations are inevitable.

\textbf{Dinella et al.} \cite{Dinella2024-NatPrecondition} attempt to synthesize human-readable preconditions by simplifying downstream conditions and lifting them earlier in code. Their tool discovers "natural" preconditions that ensure safe execution but stops short of proving equivalence to later checks. \textbf{Menguy et al.} \cite{Menguy2022-PRECA} take a black-box approach, using constraint acquisition to learn necessary input conditions that avoid failures. Their system can infer rich safety constraints even in code with third-party calls, but the results may be overly conservative and lack formal guarantees.

\textbf{Koenig and Shao} \cite{KoenigShao2021CompCertO} offer a complementary perspective through their work on \textit{CompCertO}, a modular extension of the CompCert verified C compiler. They formally prove that source-level specifications—including pre- and post-conditions at component boundaries—are preserved across compilation, ensuring semantic correctness even in open-component settings. While their focus lies in compiler verification, the emphasis on preserving input-output behavior and component-level equivalence aligns with our goals of proving \(\phi_{early} \Leftrightarrow \phi_{final}\) after transformation. Their work reinforces the idea that transformations — whether across compiler phases or within program execution — can maintain behavioral fidelity when guided by formal specification preservation.

Unlike these works—which either approximate preconditions heuristically or verify equivalence at the compiler level—our approach targets Python programs directly, focusing on synthesizing and verifying early runtime checks. We do not infer approximations but instead construct and prove assertion equivalence through a combined pipeline of LLMs, symbolic execution, and static verification.


\subsection{Ranking, Filtering, and Post-Processing of LLM Assertions}
Because LLM-generated assertions vary in correctness, post-processing methods help reduce verification burden. \textbf{Chakraborty et al.} \cite{Chakraborty2023-iRank} propose \textit{iRank}, a contrastive learning model trained to distinguish between provable and unprovable invariants using verification feedback. It prioritizes likely-correct invariants and improves verification throughput.

\textbf{Hellendoorn et al.} \cite{Hellendoorn2019-DAIKON-Ranking} applied similar filtering to Daikon's dynamic invariants, using ML models to predict which ones are likely to hold across executions. These rankers reduce noise and guide developers toward useful assertions. \textbf{So and Oh} \cite{SoOh2023SmartFix} extend these ideas to automated program repair, introducing a verifier-guided system called \textit{SmartFix} that accelerates the generate-and-verify loop using statistical models. Their framework filters candidate code patches by passing each through a safety verifier, retaining only semantically correct fixes. While their domain focuses on smart contract repair, the core methodology—leveraging verification feedback to select high-confidence candidates—parallels the challenge of filtering LLM-generated code. Unlike purely syntactic or heuristic methods, SmartFix incorporates semantic validation to ensure output correctness, aligning with our goals of verification-informed selection of early assertions.

While we do not use a learning-based ranker, our pipeline acts as a verification filter: only assertions that pass equivalence checks are accepted. Nonetheless, iRank- or VERSE-style models could complement our approach by prioritizing candidate assertions before verification, reducing tool burden and guiding LLM output quality—especially when integrated with retrieval-augmented generation.


\subsection{Neuro-Symbolic Learning for Assertion Synthesis}
Outside of LLMs, neuro-symbolic methods have been developed to generate assertions via learning-guided search. \textbf{Si et al.} \cite{Si2018-Code2Inv} introduced \textit{Code2Inv}, which uses reinforcement learning to generate invariants with feedback from a verifier as reward. Its successor, \textbf{LIPuS} \cite{Yu2023-LIPUS}, prunes the search space and adds richer reward signals to learn more expressive invariants. \textbf{Yao et al.} \cite{Yao2020-GCLN} developed G-CLN, a logic-regression model that fits nonlinear invariant functions to execution traces. It outperformed template-based inference but was limited by the expressiveness of its features.

These methods emphasize the promise of hybrid learning + verification strategies. Our project follows this direction: letting LLMs propose early conditions and verifying them through formal means. The key distinction is that we operate at the level of assertion placement and equivalence checking—not general invariant mining.


\section{Methodology}
\subsection{Overview}
Our goal is to proactively enforce security and correctness properties in Python programs by shifting runtime assertion checks earlier in execution, while ensuring that the new early assertions are \textit{logically equivalent} to the original final assertions. To achieve this, we design a three-phase pipeline that combines large language models (LLMs), program transformation, and formal verification methods. This methodology allows us to generate proposal transformations and validate their accuracy. In doing so, we seek to \textit{effectively move equivalent assertions earlier in the program}, \textit{avoiding unnecessary execution and computation} on inputs while \textit{still enforcing the same properties as the original later assertions} in the program.

\begin{enumerate}
    \item \textit{Assertion Generation:} Use a large language model (GPT-o3-mini) to generate candidate early, equivalent assertions (\(\phi_{early}\)) in specified locations (that are earlier in the program) based on program context and the existing final assertion (\(\phi_{final}\)).
    \item \textit{Program Transformation:} Create a "transform program" that introduces boolean variables \(b_{early}\) and \(b_{final}\) representing \(\phi_{early}\) and \(\phi_{final}\), respectively, and asserts \(b_{early} == b_{final}\) to encode logical equivalence of the early and final checks. For programs with \textit{multiple assert statements}, this boolean representation and combined assert would involve more variables and equivalence checks. See Figure \ref{fig:example-program}. 
    \item \textit{Testing \& Verification Pipeline:} We then apply testing \& formal methods on the transform program to verify that the LLM-added early assertion(s) enforce the same properties as the existing later assertions.

    \begin{itemize}
        \item \textbf{Symbolic Execution:} Employ CrossHair to explore execution paths of the transform program, searching for counterexamples where \(b_{early}\) and \(b_{final}\) differ.
        \item \textbf{Fuzz Testing:} Systematically generate random and boundary-case inputs designed to violate assertions, confirming that no input triggers a mismatch between early and final assertions.
        \item \textbf{Static Verification:} Apply Nagini to formally prove that for all inputs and execution paths, \(\phi_{early} \Leftrightarrow \phi_{final}\), discharging verification conditions automatically.
    \end{itemize}
\end{enumerate}

\subsubsection{Adaptations for Testing \& Verification Methods}
\paragraph{Hypothesis Testing.} Using the Hypothesis property-based testing framework, we executed each transformed program over 20 randomized and edge-case inputs. The transformed programs encode early (\(\phi_{early}\)) and final (\(\phi_{final}\)) assertions as boolean expressions and assert their equivalence. Our implementation uses Hypothesis's \textit{@given} decorator with appropriate strategy generators tailored to each function's domain (integers, floats, ranges). We configured testing parameters with \textit{@settings($max\_examples=20$)} to limit test cases while maintaining sufficient coverage. Each test function wraps the transformed program in a try-except block to cleanly capture and report assertion failures. For numerical functions involving floating-point calculations, we employed $st.floats()$ with carefully selected boundaries. The framework effectively demonstrates assertion equivalence in practice by encountering fewer failures than symbolic execution, highlighting the complementary nature of dynamic testing versus static verification approaches.

\paragraph{Symbolic Execution.}  

We ran CrossHair symbolic execution on each of the transformed programs. The transform programs are written to disk files with special docstring contracts using pre: and post: annotations that CrossHair understands. Our implementation captures both the early and final assertion conditions as boolean variables ($b_{early}$ and $b_{final}$) and explicitly checks for their equivalence. The code includes carefully defined preconditions that establish reasonable bounds for input variables (e.g., $-1000 \leq x \leq 1000$) to constrain the search space while ensuring comprehensive verification. Postconditions formally express the property that early and final assertions should be logically equivalent. The implementation invokes CrossHair through a subprocess call, captures its output, and reports any counterexamples found.

\paragraph{Nagini Static Verification.} 

To complement our dynamic and symbolic testing efforts, we use \textbf{Nagini} to formally verify the logical equivalence $\phi_{\text{early}} \Leftrightarrow \phi_{\text{final}}$ for transformed Python programs. Built on the Viper intermediate verification language, Nagini supports PEP 484-style type annotations and permission-based heap access control, but imposes strict constraints: programs must be statically typed and avoid dynamic features like \texttt{eval} or runtime field creation. Adapting programs for Nagini required \textbf{adding type annotations and contracts, minimally reformatting control flow, and eliminating unsupported language features}. Our verification process follows a two-phase strategy: first testing the original program with dynamic and symbolic methods, then adapting it for Nagini while preserving logical structure. This approach enables us to distinguish between true semantic failures (indicating assertion inequivalence) and compatibility issues (reflecting tooling limitations rather than transformation failures).

We evaluated all 45 functions using our three verification methods—fuzz testing, symbolic execution (CrossHair), and static verification (Nagini).

\paragraph{Verification Outcomes.}
Fuzz testing was the most permissive method, successfully executing across all 45 functions without encountering assertion failures. This method relies on generating randomized input data and is generally effective at identifying shallow bugs or edge cases. However, it does not guarantee full path coverage, making it less reliable for verifying correctness in complex control flow scenarios. 

CrossHair, which uses symbolic execution to analyze possible execution paths, was more selective—only 17 functions passed its checks. These functions were typically lower in complexity and had predictable, linear execution paths. CrossHair failed on functions with randomness, deep nesting, or heavy use of mathematical transformations, where symbolic solvers either timed out or generated counterexamples.

Nagini, the static verification tool, was the most stringent. It successfully verified only 10 functions, all of which had also passed CrossHair. The overlap between Nagini and CrossHair indicates that static verification benefits from structural simplicity and a limited scope of behaviors. Functions that passed Nagini were generally those with no branching, recursion, or reliance on non-determinism—attributes that make a function more amenable to logical inference and type-based guarantees.

\paragraph{Fully Verified Functions.}

 Functions like \verb|transform_data|, \verb|ascii_average|, \verb|odd_sum_validator|, \verb|string_pattern_score|, and \verb|square_accumulator| achieved full verification across all three tools. These functions share common traits: they use simple data structures (integers, lists, strings), have sequential logic, and avoid branching, loops, or random number generation. As such, their behavior is easy to model both dynamically and statically.

\paragraph{Validated Functions.}

 Functions that passed fuzzing and symbolic execution but failed Nagini included \verb|process_complex_number|, \verb|circle_area_diff|, \verb|triangle_checker|, and \verb|hypotenuse_diff|. In many of these cases, the logic was sound but relied on constructs like math library calls, type conversions, or moderately nested control flow, which made static verification challenging. This suggests that Nagini's inference system struggled with external dependencies or floating-point operations.

\paragraph{Rejected Functions.}

 A majority of functions—especially those using randomness (\verb|function_11|, \verb|function_13|, \verb|function_17|, etc.), factorial calculations (\verb|factorial_square_root_mod|, \verb|factorial_root_modulo|, \verb|factorial_modulo_processor|), or non-linear accumulation (\verb|sum_until_limit|, \verb|fibonacci_counter|)—were rejected. While these functions often passed fuzz testing, they failed symbolic execution due to the presence of non-determinism or high path complexity, and static verification was infeasible due to branching logic and mathematical abstraction.

\paragraph{Analysis and Takeaways.}

 Our results demonstrate clear differences in the strengths and weaknesses of the three tools:

\begin{itemize}
    \item \textbf{Fuzz testing} is excellent for broad behavioral validation but can miss subtle logic errors or corner cases in complex branching.
    \item \textbf{CrossHair} offers deeper path analysis but struggles with randomness and complex arithmetic.
    \item \textbf{Nagini} is useful for verifying straightforward, strongly-typed logic, but cannot handle dynamically complex or non-linear code well. We elaborate this on the subsequent discussion section. 
\end{itemize}
Additionally, these outcomes validated our program complexity scoring model. For instance, the average complexity score for fully verified functions was 4.7, while the average for rejected ones was 6.1. In summary, this layered evaluation approach allowed us to confirm that our weighted complexity model aligns closely with real-world verification difficulty.

\section{Discussion [NEED TO REDO, MAKE MORE RELEVANT]}

\subsection{Evaluating the Transformation Pipeline.}
Our results demonstrate that early assertion transformation is both feasible and beneficial across a wide range of Python programs. The majority of transformed functions preserved correctness under fuzz testing and symbolic execution, and our complexity analysis showed that transformation success was not limited to trivial cases. As noted in the previous section, most of the functions fell into the medium complexity range, and a sizeable portion were high or very high complexity—indicating that our approach can, within reason, scale to nontrivial control flow and data manipulation patterns. 

However, transformation success was not universal. A small subset of functions failed fuzz testing or symbolic checks \textbf{due to semantic mismatches between early and final assertions.} These failures often stemmed from subtle control flow dependencies or implicit assumptions in the original code that were not preserved during transformation. This highlights a key challenge: while LLMs can generate plausible early assertions, ensuring their logical equivalence to final checks remains nontrivial, especially in the absence of formal specifications. \textbf{We don't particularly focus on evaluating the LLM's capability itself, but rather our ability to evaluate the correctness of candidate early assertions in a systematic, tested, and ideally provable manner. }

\subsection{Nagini as an Experimental Formal Verifier.}
To provide stronger correctness guarantees, we incorporated Nagini to formally prove the equivalence $\phi_{\text{early}} \Leftrightarrow \phi_{\text{final}}$ in transformed programs. However, we encountered significant practical constraints: of our 45 transformed programs, only 10 could be formally verified even after adaptation.

This limitation reflects Nagini's design choices rather than flaws in our transformation approach. The formal verification tool was designed for mathematically rigorous proofs of specific program properties, not as a general-purpose Python verifier. While these adaptations preserved the core semantic properties, they created a gap between the original transformed program and its verifiable representation.

We treated Nagini as a high-assurance oracle for a curated subset of cases, not as a universal verifier. This approach preserves evaluation integrity while leveraging Nagini's formal verification capabilities where applicable. In the final phase of the project, we plan to apply Nagini more deliberately to a filtered set of transformed programs that align with its verification model, allowing us to explore its verification power more systematically without the confounding effects of program incompatibility.

\subsection{Limitations and Future Directions.}
Our pipeline currently assumes that early and final assertions are syntactically extractable and structurally comparable. This limits its applicability to programs where assertions are deeply embedded in control flow or rely on runtime state. Additionally, while our LLM-based transformation is effective, it lacks formal guarantees and occasionally introduces semantic drift. \textbf{Future work could explore integrating specification-aware prompting or constraint-guided generation} to improve alignment rather than the \textbf{simple black-box approach} we currently employ. 

On the verification side, our experience with Nagini suggests a need for more flexible and transformation-aware verifiers. One promising direction is to co-generate both transformed code and its accompanying contracts, enabling tighter integration with tools like Nagini from the start of the transformation pipeline. Alternatively, hybrid systems that combine static and dynamic reasoning—e.g., by using symbolic execution to validate contracts before formal verification—could offer broader coverage without sacrificing rigor.

\subsection{Broader Implications.}
Our work advances the field of proactive program safety by demonstrating that assertions can be automatically shifted earlier in execution while preserving their logical integrity. By enabling violations to be caught at the earliest possible point—before critical operations execute or errors propagate—SENTINEL contributes to more robust, efficient, and secure Python programs. Our pipeline proves that combining LLMs for \textbf{assertion generation with rigorous verification techniques can reasonably enhance fail-fast behavior while reducing risk of false positives}. These findings have implications beyond Python, suggesting a generalizable approach to runtime enforcement that could benefit safety-critical systems, reduce computational waste, and provide developers with stronger guarantees about program behavior across varied execution paths.
